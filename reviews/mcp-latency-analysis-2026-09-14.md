**MCP 读取性能诊断 · 2026-09-14**

用户关注的是 MCP 本身的效率；全量阅读、先筛后读或其他选题顺序由使用者决定。本轮测量服务与协议开销，补齐评测计时，未改生产工具、数据投影或选题策略。

此前“哪题容易切入”的 99 秒是一次 `gpt-6-astra` ultra 模型运行的总耗时，包含客户端、模型和工具链。原事件记录显示调用重叠批次为 2 → 1 → 8 → 16 → 1，25 次详情读取已经并发；事件没有时间戳，无法把原总耗时精确拆成模型或 API 用时。

在同一机器、Node v22.16.0、提交 `89e5cb8` 的 111 题目录上，新启动内存 API/MCP，完整读取 25 道未解决量子算法题。每种配置重复三次，以下为整批客户端墙钟中位值，单位毫秒：

| 路径 | 串行 | 并发 8 | 并发 25 |
| --- | ---: | ---: | ---: |
| 直接 API | 518 | 512 | 500 |
| 官方 SDK → MCP → API | 575 | 523 | 522 |

进程启动另计 2.33 秒。没有远端网络或外部模型调用；不能把本地半秒从此前 99 秒中直接相减，或据此预测所有客户端延迟。可复用探针复跑得到 MCP 三种配置 578 / 539 / 539 毫秒，符合初次观察。[初次原始数据](mcp-latency-baseline-2026-09-14.json)，[可复用探针复跑](mcp-latency-probe-verification-2026-09-14.json)。

25 题返回体积：单份紧凑 JSON 452,231 字节；API 实际正文 508,392 字节；MCP HTTP 正文约 990 KB，含文本 JSON、structuredContent 和协议封装。两种表示增加传输字节，但不能据此断言宿主把两份内容都输入模型。

255 个研究条目的 provenance 共 95,885 字节，其中与父级完全相同的字段占 73,185 字节，约为单份 JSON 的 16.2%。其余条目定位信息仍需要保留。这个数是结构去重机会，不是已经实现的压缩收益；新的共享格式也有自身开销。Statement 的 Markdown body / clauses，以及 ledger references / authored bibliography 虽有内容重叠，分别承载不同信息，不能简单删除其中一份。

后续生产优化建议，均保持调用者决定读取范围：

1. **提供通用批量详情读取。** `get_problems(ids, view)` 读取调用者给定的题目集合，保留输入映射、完整科学内容和应保留的服务正文。复用单题投影，在一次请求中使用同一目录版本。它不筛题、不排序，也不强制选题流程。超出明确响应预算时整批报错并给出拆分信息，避免静默漏题。
2. **提供可选紧凑研究格式。** 把完全相同的公共 provenance 放到父级，条目保留自身 section/index/locator；清楚声明继承规则，并通过展开后与原详情逐字段相等的回归证明无损。单题旧格式继续兼容。书目只能在保留完整信息及映射的前提下共享。
3. **用同场景计时验收效果。** 比较完整读出集合、内容等价、工具调用数、返回字节和端到端时间，不用少读题或缩短正文制造提速。批量工具减少调用数量，不保证模型一定采用，也不保证总延迟按相同比例下降。

本轮已增加 [measure-reads.mjs](../mcp/eval/measure-reads.mjs)，独立测量完整读取耗时和体积；[run-research.py](../mcp/eval/run-research.py) 改为流式接收事件，记录单调时钟、首末工具事件和每次工具调用的宿主观察时间，仍剔除 reasoning 内容。`--case 2 --history-from DIR` 可复用原前文进行选题单场景复测。尚未据此重新运行外部模型，不宣称端到端提速已得到验证。
