## 结论与优先级

当前基础值得保留：HTTP/stdio 共用业务 adapter，公共 HTTP 强制只读，服务负责权威状态；已有分页、稳定标识、资源模板、热更新和完整研究流程测试。

近期应优先改善研究上下文的完整性、检索召回和两种传输的一致性。添加工具数量、复杂编排或语义检索应放在这些基础问题之后。

| P1 | 修复 context 裁剪和 bundle 内容标识 | 模型拿到明确、可追踪的正式问题陈述 |

## 1. Context 的预算行为与内容标识

位置：`service/src/read-models.ts:185–224`。

当前先放入 `problem.body`，再放 statement、clauses、claims、references，按字符数直接截断。导出器的 `problem.body` 包含 Source、Progress、Comment 和 References，正式 Statement 单独存放（`scripts/export-ledger.mjs:181–194`）。实际索引目录有 104 条记录：

| tokenBudget | statement section 为空 | statement section 非空但截断 |
| --- | ---: | ---: |
| 200 | 104 | 0 |
| 1000 | 26 | 35 |
| 2000 | 4 | 4 |
| 8000（默认） | 0 | 0 |

这些计数专指独立的 statement section；背景中可能提到部分问题，但不能替代完整正式陈述。默认预算下陈述完整，问题集中在工具明确支持的较小预算。

`clauseIds` 只影响条款概要等部分；statement 仍使用全文。字符裁剪可能发生在数学表达式中间。`approximateTokens` 只按 section 文本字符数除以四计算，不含 JSON 外壳等开销，不是严格的模型 token 上限。

另一个实测问题：同一真实问题分别传入预算 200 和 250，返回文本长度不同（800 / 1000 字符），但 `bundleId` 相同。只在内存修改 `problem.body`，完整返回内容变化而 bundle ID 也不变。原因是 ID 仅覆盖 `(record id, digest)` 与 section 的 cut/full 标记；多数 record 的 digest 为 null，截断位置和实际返回文本不进入散列。

另有两个与科学语义直接相关的问题：

- **权威状态未传入 context。** 当前 9 条 `Solved` 问题的 clause 均显示内部证据状态 `[open]`，context 又没有顶层 status。目录已解决和服务尚无验收证据是不同含义，不能让模型据后者误判问题仍未解决。应传入 frontier 已有的 `status` / `statusSource` 并解释层次，保持问题状态只有 `Solved` / `Unsolved`，不虚构审核或更改权威结论。
- **修订后的既有成果可能消失。** frontier 沿 clause lineage 找到成果，但 context 在第 200 行又按当前 clause ID 精确匹配。conformance fixture 的内存 v2 模拟中，frontier 仍返回旧版本已验收的 `1/2` 下界及 `symmetric subfamily only` 条件，context 的 acceptedClaims 为空。此项是模拟版本演进复现，不是当前目录已有记录损坏。应复用 frontier 的 claimIds / lineage，同时在上下文保留 bound 的值、方向、条件和证据引用，不能只保留标题。

建议：

- 为当前 statement / 所选条款及必需定义优先分配空间；完整陈述放不下时明确返回不完整状态、所需预算或可继续读取的资源，不把截断文本呈现为完整研究输入。
- 按语义段落或完整条款裁剪；区分核心内容与可选背景、讨论。
- 用规范化的实际内容和来源版本计算 bundle digest；区分参与构建的来源与真正展示的内容，避免把未显示的 statement 标成已读。
- 为不同预算但相同 cut/full 形状、来源修订、选择条款、长公式与非英文内容加入回归检查。

## 2. 搜索漏掉正式陈述中的术语

位置：`service/src/index.ts:127–141,178–197`。

`search_text` 仅包含 title、keywords、aliases 和 problem.body，没有当前 statement。查询按前八个空白分词逐项做 AND/LIKE 匹配，默认按 title 排序，没有相关性分数或命中片段。

实测中，`separable` 搜不到 “Absolute separability from spectra”，`bipartite` 搜不到对应的 purification additivity 问题，尽管其正式 statement 包含这些词。

建议先索引当前 statement 和条款原文，并返回简短的 `matchedFields` / snippet。之后根据固定查询集评估相关性排序、词形与领域缩写处理。暂不据此断言需要 embedding；当前已经存在可直接修复的确定性召回缺口。

## 3. HTTP 与 stdio 的边界行为不一致

位置：`mcp/src/http.ts:54–74`、`mcp/src/server.ts:22–47`。

HTTP 使用官方 SDK 和 `fromJSONSchema`，并提供只读 annotations。stdio 独立手写 JSON-RPC，没有执行 inputSchema 校验，也没有输出 annotations。

无网络 subprocess / mock-fetch 探针复现：

- initialize 原样接受并返回 `protocolVersion: "completely-unsupported"`。
- `jsonrpc: "definitely-not-2.0"` 的 ping 仍得到成功响应。
- 无 ID 的 tools/list notification 仍得到 result。
- 负数 limit、非法 status 会进入上游请求；服务本身可能拒绝，但 MCP 边界未按声明 schema 校验。
- cancellation notification 被忽略，adapter 的 fetch 只有固定 20 秒 timeout。

建议抽出共同的 MCP server 注册函数，让 stdio / HTTP 共用官方 SDK、校验和结果构造。如果保留 stdio 零依赖是明确产品要求，至少共用验证器并显式实现受支持版本协商。旧版初始化不能对任意请求版本声称支持，参见 [MCP 2025-11-25 lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle#version-negotiation)。

## 4. 认证写工具尚未利用幂等回放

位置：`mcp/src/adapter.ts:25–36`、`service/src/api.ts:460–474`。

服务已有 Idempotency-Key 回放支持，adapter 没有公开或转发该键。上游 timeout 固定 20 秒；结果也丢弃 Retry-After 等响应头。如果写入已完成但响应丢失，agent 的重试可能产生重复记录。当前公共 HTTP 不开放这些写工具，因此该项主要影响认证 stdio。

建议让同一逻辑写入携带稳定幂等键，以 HTTP header 传递，不能混入科学记录 payload。错误需保留状态码、是否可重试、等待时间；对 POST 的重试须与同一幂等键绑定。增加“服务写成功后断连再重试”的测试。

## 5. Schema 与工具发现的改进

位置：`mcp/src/adapter.ts:98–125`、`mcp/src/server.ts:5–6,36,45,64–65`。

- `end_trajectory.cost`、review 的 independence / checks 等仅声明 object/array，真实字段和枚举存在于 contract 中。应从 contract 派生有用的 MCP schema，避免分别手写漂移；也避免把整套巨大 contract 重复塞进每个工具描述。
- `upload_artifact` 允许 text/base64 都缺失或同时出现。实测都缺失时发送空上传；应在边界验证合法输入形态。
- 无 API key 的 stdio 仍公布全部 25 个工具，其中 8 个写工具无法匿名调用。建议默认按只读/认证能力展示可用工具，并说明模式。
- `claim_queue_item` 只是读取队列第一项，没有 claim、reservation 或 lease。若保留此行为，应明确说明“不预留”；命名更新需兼容既有客户端。
- 两种传输仅返回文本 JSON。先给 search/status/context 提供稳定 `structuredContent` 和 `outputSchema`，并保留兼容文本表示。它们属于协议支持的可选能力，不是当前文本输出违反协议；见 [MCP tools 规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#structured-content)。结构化输出本身不保证节约 token，仍需实测客户端呈现方式。
- 可以提供少量研究/审核工作流模板，以及按章节读取和引用资源的方式；这是产品增强，不应让 MCP 承担科学结论决策。
